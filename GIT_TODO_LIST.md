## Blockers

**Push to a PR head branch deadlocks the repo forever** (verified). `internal/gitrepo/http.go:400` holds the per-repo `sync.Mutex` across `transport.ReceivePack`. go-git runs PostReceive synchronously, which calls `AfterRefUpdate` at `manager.go:884`, which calls the forge subscriber inline, which reaches `refreshPullRef` at `internal/forge/pulls.go:138` and takes `LockRepo` on the same repo. The mutex is not reentrant. Any push to a branch that is the head of a same-repo open PR hangs, and every later push, web commit, merge, mirror sync and maintenance run on that repo hangs behind it. Same path via SSH, `CommitToBranch`, `UpdateRef` and mirror `fetchInto`. Each hung push also holds a transfer-semaphore slot, so after 32 of them clones get 503 instance-wide.

**Reserving `admin` breaks upgrades and bootstrap** (verified). `pkg/utils/username.go:55` reserves `admin`, `git`, `docs`, `new`, `images` and friends. `config.example.yaml:54` ships a bootstrap user named `admin`, and `bootstrap.go:31` now rejects reserved names before checking whether the user exists, so the server refuses to start with `bootstrap seeding: bootstrap user "admin": name is invalid or reserved`. Migration `202610140003` then silently renames any such user or org to `admin-user` with only a warn log, rewrites the `namespace` column on image and artifact repos, but never calls `RegistryAccess.MoveRepository`, so Distribution storage stays under `repositories/admin/` and every image in that namespace 404s. Org-scoped token `scope_id` values are not rewritten either. The reserved list only matters for the root-level git page, so renaming image and artifact namespaces at all is over-reach.

**Scoped tokens are not scoped outside the git helpers** (verified). `internal/rpc/interceptors.go` never reads `user.Scope`, and `token_handler.go:303` `canPush` grants docker push by namespace ownership or org membership with no `ScopeAllows` call. Worse, `services/token.go:63` returns before the `IsScoped` refusal when no scope is requested, so a scoped credential can call `CreateAPIToken{name}` and receive a permanent unscoped token. Actions job tokens are scoped API tokens owned by the triggering user, so any workflow step can mint a permanent token with that user's full roles. If an admin pushes or comments on a repo with a workflow, the workflow author gets admin.

**The runner hands every job root on the host** (socket and options verified). `pkg/runner/docker.go:118` bind-mounts `/var/run/docker.sock` into every job container whenever it exists, and `container.options` passes `--privileged` and `-v` straight into the HostConfig. `pkg/runner/actions.go:729` resolves upload and download artifact paths on the host, so `path: /home/runner/.dfcli/runner.json` uploads the runner token and `download-artifact` can write to `/etc/cron.d`. `commands.go:107` still honors `::set-env::` and `::add-path::` (the CVE-2020-15228 class). Images are pulled only if missing (`docker.go:213`), so one job can `docker tag evil ubuntu:24.04` for everyone after it.

**Expressions are evaluated twice** (verified). The server interpolates `run`, `env`, `with` and `name` at `internal/actions/tasks.go:244,298`, then the runner interpolates the same strings again in `pkg/runner/steps.go` and `actions.go:308`. The runner has `secrets` in context. An issue titled `${{ toJSON(secrets) }}` used via GitHub's recommended `env: TITLE: ${{ github.event.issue.title }}` pattern dumps every secret. Combined with `triggers.go:277`, where fork-PR approval is keyed on who performed the triggering action rather than the PR author (a maintainer clicking "request review" runs the fork's head workflow with all secrets and the maintainer's write token), and `tasks.go:229` handing every system secret to every repo and every org secret to every org repo, this is the actions security model not being there yet.

**Unbounded matrix expansion runs inline in the push path**. `internal/actions/workflow.go:695` has no cap on the cartesian product (GitHub caps at 256) and `runs.go:122` expands it synchronously inside `createRun`, which runs inside the push or PR request goroutine before any approval. Ten keys with ten values each is ten billion job rows. Any fork PR author can OOM the server.

**Stored XSS on the app origin through `-/raw/`** (server side verified). `internal/gitrepo/reads.go:531` serves `.svg` as `image/svg+xml` and falls through to `http.DetectContentType` for `.htm` and extensionless files, and `http.go:484` sets `Content-Disposition: inline` for `text/*` and `image/*`. There is no CSP anywhere. The frontend reviewer reports the session token lives in `localStorage.distroface_session`. One click on a shared raw link is account takeover.

**Repo-tier mail settings inherit the instance SMTP password** (verified). `internal/settings/merge.go:36,45` allows the whole `mail` subtree at org and repo scope, and `resolver.go:226` overlays tiers field by field. A repo owner sets only `smtp_host` at repo scope, `worker.go:216` then authenticates to that host with the system username and password. Setting only `from_address` instead sends mail as `it-security@corp.com` through the trusted company relay, and a repo-level `max_per_minute: 0` removes the throttle. With open registration this is any user.

## High

- `internal/gitrepo/lfs.go:194`: an upload batch naming an oid that already exists in the shared blob CAS links it to the caller's repo with no bytes transferred, so anyone who learns a private blob's sha256 can download it. `lfs.go:92` classifies the operation with strict `json.Unmarshal` while the handler uses a lenient decoder, so a body with trailing junk passes only the pull check and reaches the upload branch anonymously.
- `internal/gitrepo/manager.go:343` auto-links every same-named image and artifact repo to a newly created git repo, and `repo_access.go:71` unions access through that link. Any org member creates public git repo `acme/app` and the private image `acme/app` becomes pullable by anonymous. The reverse also holds: a member with no push on image `org/prod` gains it by creating git repo `org/prod`. `services/git.go:1082` `LinkRepository` lets a repo admin collaborator link any package in the namespace with no check on the package itself.
- `internal/forge/pulls.go:454`: `allow_maintainer_edits` is set by the PR author, not the fork owner, and it grants base writers `DeleteHeadBranch`, `UpdateBranch(rebase)` and `ApplySuggestion` on someone else's fork. `preReceive` has no push-permission check of its own, so this is the only gate.
- `internal/forge/notifications.go:353` (verified): `tokenKey` reads `jwt_secret` from the settings table, which is empty whenever the operator sets `auth.jwt_secret` in config. The unsubscribe HMAC key degrades to `sha256("notifications:")`, and `UpdateNotificationPrefs` is a public procedure, so anyone can rewrite any user's notification prefs. Tokens never expire.
- `internal/gitrepo/signing.go:184`: GPG "Verified" matches the committer email against the uploaded key's own UIDs, not the account's email. Upload a key with UID `ceo@corp.com`, pass the possession challenge, and signed-commit rules accept you as the CEO. The SSH path at `:238` does this correctly.
- `internal/gitrepo/fetch.go:36` and `mirror/git_sync.go:239`: `safeTransport` only covers HTTP. SSH upstreams and SSH push mirrors dial with a plain `net.Dialer`, and scp-style `10.0.0.5:a/b` parses as `ssh://`. Each sync is an internal port scan with results in `mirror_last_error`.
- `services/gitrefs.go:277`: renaming the default branch needs only code write, moves `default_branch` and HEAD to the new unprotected name, and protections match by pattern and do not follow. `services/git.go:649` `SyncFork` and `forge/pulls.go:564` `UpdateBranch` apply `BypassPullRequest` to branches that may themselves be protected.
- `services/gitfiles.go:325`: compare endpoints, which are anonymous reads, call `FetchLocal` into the base repo and create `refs/distroface/compare/<sha>` with no cleanup, no quota, no hooks and no portal check. Anyone can grow a public repo's object store without bound.
- `services/team.go:347`: `ListTeams`, `GetTeam`, `ListTeamMembers` and `ListTeamRepos` need only `organizations/read`, which the `user` role has as `*`, and have no membership check. The default team has `includes_all_repos`, so any registered user lists every private repo name in any org.
- `services/project.go:118` and `forge/projects.go:170`: `GetProject` is an identity procedure, org boards are readable by anyone, and cards render title, labels, assignees and repo name with no per-issue `CanSee`. Private-repo issues on a public org board are readable by anonymous.
- `internal/mailer/inbound.go:111` and `forge/inbound.go:33`: reply-by-mail tokens are reusable for 30 days, bound to nothing about the sender, and never check `IsActive`. Nothing checks `Auto-Submitted` or sets it outbound, so two out-of-office responders produce an infinite comment and mail loop. `inbound.go:53` falls back to plaintext IMAP LOGIN when STARTTLS fails.
- `internal/gitrepo/access.go:277`: `identityLevels` returns early for owners and org admins with an empty units map, and the scoped branch copies only units. Every scoped token or Actions job token owned by the repo owner gets public read only. Private repos look not found and pushes fail. This also breaks LFS over SSH for owners because `lfsPrincipal` always sets a scope.
- `internal/mirror/git_push.go:44` (verified): `SchedulePushMirrors` has no callers. `sync_on_push` defaults to true in the model and does nothing.
- `internal/mirror/git_import.go:915,1029`: the issue or PR row is written before comments and reviews are fetched, so a rate-limit or deadline inside `importComments` makes resume skip that item forever. `git_import.go:291` maps upstream usernames and emails to local accounts, so a hostile upstream attributes comments and approvals to your local admin.
- `internal/gitrepo/diff.go:293`: `hunksFromChunks` advances the line counters through leading context, then re-emits that context and advances again. Every hunk with leading context has wrong line numbers, so review comments and suggestion-apply anchor to the wrong lines. The reviewer verified this by executing the logic.

## Medium and lower, grouped

**Secret key material.** Actions secrets, mirror SSH keys and notification tokens all derive from the JWT secret, which by default is stored hex-encoded in the same database. Setting or rotating `auth.jwt_secret` later makes every sealed value undecryptable. `internal/actions/secrets.go:79` (verified) only warns and drops the secret, so jobs run with it missing and deploys fail with no user-visible cause. `git_sync.go:243` swallows the key failure and may fall back to the server's `SSH_AUTH_SOCK`. Push mirror `AuthToken` and pull mirror `auth_token` are plaintext in the DB. `mirror.go:44` keeps a stored token when the URL changes, so a co-admin can point it at `evil.example` and receive the PAT.

**Branch protection and merge rules.** `forge/merge.go:113` skips dismissed reviews before picking the latest per reviewer, so dismissing a change request revives that reviewer's older approval. `merge.go:140` only enforces CODEOWNERS groups that resolved to at least one user, so a typo or an empty team fails open. `merge.go:155` passes required status checks when zero statuses exist. `pulls_push.go:58` never disarms auto-merge on a new head push, so a fork author can get a malicious commit merged in the armer's name. `merge.go:396` ignores the `truncated` flag from a 1000-commit walk, so rebase merges of larger PRs drop commits. `hooks.go:291` walks from head with only `old` marked seen rather than excluding its ancestors, so signed-commit and linear-history rules both false-reject new branches and miss anything buried under 1000 newer commits. `hooks.go:226` treats an ancestry error as "not forced".

**Issues and PRs.** `forge/issues.go:414` `setState` has no merged guard, so `UpdateIssue{state:open}` reopens a merged PR, and `BulkUpdateIssues` builds its actor from the issues unit but accepts PR numbers. `services/issue.go:158` list and search check only code visibility, never the issues or pulls unit level. `forge/dependencies.go:72` is a depth-50 DFS with no visited set, so a diamond lattice of about 80 issues pins the CPU on the next `AddDependency`. `forge/reviews.go:474` applies suggestions using the original line numbers against the current head with no remap. `notifications.go:117` never re-checks `CanSee`, so removed collaborators keep receiving full comment bodies by mail and in their bell, and `@org/team` mentions skip the access check. Notify runs about eight queries per recipient synchronously inside the comment RPC.

**Lifecycle and cleanup.** `manager.go:473` `Delete` leaves casbin grants, SSH and deploy keys (unique fingerprint blocks re-adding), the settings row and repo-scoped secrets, variables and runners. `manager.go:559` `Move` only moves name-linked packages, best effort, and leaves `org_team_repos` rows so the old org's teams keep seeing the private repo. `stores/teams.go:190` `RemoveOrgMember` never deletes team memberships. `settings/resolver.go:143` caches repo-to-org and is not invalidated on move, so a transferred repo keeps the old org's SMTP and quota. `manager.go:546` transports open the storer before waiting on the lock, so a push waiting during a rename writes into the old path and recreates a ghost directory that blocks `Create` at that name forever with no repair path (PLAUSIBLE). The `webhooks` FK addition makes gorm sqlite recreate the table under `foreign_keys=on`, which cascades a delete through `webhook_deliveries` on first boot (PLAUSIBLE, high confidence).
